# **1\. 분석 배경 — 왜 KV cache인가**

  KV cache를 통해 LLM은 토큰을 하나씩 생성하면서 앞서 계산한 Key-Value를 저장해 두고 재사용한다. 매번 다시 계산하는 낭비는 사라지지만, 문맥이 길어질수록 저장량이 선형으로 증가하여 GPU의 HBM 용량을 빠르게 소진한다.

  즉 KV cache는 "연산 병목"을 "메모리 병목"으로 치환한 구조이며, 계산을 아끼려다 메모리가 한계에 도달하는 상황이 발생한다. 이 병목을 푸는 접근은 SW, HW 두 방향으로 갈린다.

| 구분 | SW 진영 | HW 진영 |
| :---: | :---: | :---: |
| 전략 | 데이터를 작게 만든다 | 담을 공간을 넓힌다 |
| 방법 | 압축·양자화, 어텐션 구조 개선 | 메모리·스토리지 계층 확장 |
| 장점 | 기존 GPU에 소프트웨어만으로 즉시 적용 | 원본 보존, 정확도 손실 없음 |
| 단점 | 압축률을 높이면 정확도 하락 위험 | 새 하드웨어를 전제로 요구 |
| 대표 기술 | TurboQuant, KIVI, DeepSeek MLA | ITME, InfiniGen, PNM/CXL |

  본 과제는 각 진영에서 1건씩을 선정해, 어느 쪽이 우월한지가 아니라 관점에 따라 평가가 어떻게 갈리는지를 비교하는 Agentic RAG 시스템을 설계·구현한다.

# **2\. 대상 기술**

| 진영 | 기술 | 논문 | 핵심 주장 |
| :---: | :---: | ----- | ----- |
| SW | TurboQuant | Online Vector Quantization with Near-optimal Distortion Rate (2025-04) | KV cache 3비트 양자화, 어텐션 처리 최대 8배 |
| HW | ITME | Inference Tiered Memory Expansion with Disaggregated CXL-Hybrid Memories (2026-06) | CXL-Hybrid 계층적 메모리 확장, 처리량 1.80배 |

## **2-1. TurboQuant 선정 사유**

* 저비트에서도 품질을 유지하려는 설계. 3bit 수준의 낮은 precision까지 내려가면서 품질 유지를 시도한다. 일반적으로 비트를 줄이면 메모리는 줄지만 quantization error가 커지는데, TurboQuant는 벡터 분포를 양자화하기 좋은 형태로 변환하여 손실을 줄인다. 단순한 FP16 → INT3 절단이 아니다.

* 비즈니스 요구와의 정합성. 데이터센터 서빙에서 정확도는 SLA와 직결되므로, 정확도 손실을 정교하게 통제하려는 접근이 평가 대상으로 적합하다.

## **2-2. ITME 선정 사유**

* 논문 단계를 넘어 제품 단계까지 검증되었다. FPGA로 시제품을 구현하고, SK하이닉스의 실제 CXL 메모리 제품(CMM-DDR5)으로도 검증했다. "공개 정보 기반 추정"이 전제인 과제 성격상 근거가 실재하는 기술이라는 점이 실질적 이점이다.

* 원본 KV에 변형을 가하지 않는 순수 공간 확장이다. InfiniGen은 필수 KV 항목만 프리패치하여 선별 요소가 섞이고, PNM/CXL은 연산 자체를 메모리 쪽으로 옮겨 제3의 접근에 가깝다. ITME만이 원본 KV를 그대로 두고 저장 계층만 확장한다.

* 기존 메모리 계층을 확장하는 구조다. GPU HBM → CPU DRAM → Local SSD → Remote Storage 계층에 새로운 CXL-hybrid memory tier를 삽입하는 방향으로 확장한다.

# **3\. 설계**

## **3-1. 기술 선정 방식**

2안 — Human 기반

  본 과제의 분석 가치는 "무엇을 고르느냐"보다 "고른 둘을 얼마나 다층적으로 비교하느냐"에 있다. 선정을 에이전트에 맡기면 선정 근거의 재현성이 떨어지고 비교 기준이 명확하지 않을 위험이 있다. 대신 선정 기준(접근의 대립성 · 전제 조건의 비대칭 · 검증 주기 차이)을 명시하여 주관성을 통제한다.

### **선정 결과 — BAAI/bge-m3**

평가 결과 BGE-M3가 Hit@1, Hit@3, MRR 모든 지표에서 가장 높은 성능을 기록하였다. 특히 정답 청크를 검색 결과 상위에 배치하는 능력을 나타내는 Hit@1과 MRR에서 가장 우수한 결과를 보여, 기술 조사 Agent가 신뢰도 높은 근거 문서를 우선 활용하는 데 적합하다고 판단하였다.

또한 본 프로젝트는 한국어 질문으로 영어 기술 논문을 검색하는 Cross-lingual 환경이며, CXL·KV cache·FPGA와 같은 전문용어 및 약어, 비교적 긴 기술 문서 청크를 처리해야 한다. 이러한 요구사항과 자체 검색 성능 평가 결과를 종합하여 **최종 Embedding 모델로 BGE-M3를 선정하였다.**

# **4\. 평가 관점 및 기준**

## **4-1. 전제 및 공통 판정 규칙**

### Agent의 기술에 대한 판정은 2단계로 이루어진다.

| 단계 | 내용 |
| :---: | ----- |
| 1단계 | 각 조사 질문을 근거 강도에 따라 상 / 중 / 하로 채점한다. |
| 2단계 | 채점 결과를 집계하여 축 등급을 부여한다. State의 verdict에는 축 등급을 기록하고, 질문별 상·중·하는 signals에 남긴다. |

### **\[질문별 채점 규칙\]**

| 등급 | 조건 |
| :---: | ----- |
| 상 | 1차 자료로 확인 — 공식 발표, 제품 문서, 논문, 시장 리포트 |
| 중 | 간접 근거만 확인 — 언론, 블로그, 커뮤니티 토론 |
| 하 | 근거를 찾지 못함 |

판정은 판정 등급 · 근거 URL 1건 이상 · confidence를 함께 기록한다. 출처가 2건 미만인 판정은 confidence: low로 표기한다.

## **4-2. 선정 도메인 — 데이터센터 · 클라우드 서빙**

### **선정 사유**

1. KV cache 병목이 비용으로 환산되는 환경이다. HBM 점유는 곧 동시 처리 가능한 요청 수를 결정하므로 두 기술의 효과를 같은 단위로 평가할 수 있다.

2. 두 기술 모두 적용 가능하다. 비교축이 "적용 가능성"이 아니라 "도입 조건(비용 구조·리드타임·리스크)"이 되어 네 관점이 균등하게 작동한다.

3. 공개 자료(시장 리포트, 벤더 로드맵, 표준화 동향)가 풍부해 관점별 근거 수집의 편차가 작다.

## **4-4. 시장성 관점**

3개 축으로 구성한다.

### **축 1 — 시장 규모와 성장성 (수요 불명확 / 수요 존재 / 수요 확실)**

조사 질문

1. KV cache 메모리 병목이 데이터센터의 비용·성능 문제로 언급되는가

## **4-7. 종합 관점**

관점별 판정을 종합하되, 관점 간 상충 지점이 명시적으로 드러나도록 구성한다. 종합 Agent는 다음 다섯 질문을 통해 상충을 탐지한다.

| 탐지 질문 | 확인 대상 |
| :---: | ----- |
| 성능 향상이 다른 품질 또는  안정성 저하와 함께 나타나는가 | 메모리 절감·throughput 향상과 정확도·응답 품질·안정성의 관계 |
| 한 자원의 절감이 다른 자원 또는  비용 증가로 이어지는가 | GPU 메모리 절감 대신 CPU·bandwidth·storage·운영비가 증가하는지 |
| 기술적 이점이 운영 복잡도나  적용 난이도를 증가시키는가 | 성능 개선과 배포·통합·유지보수 부담의 관계 |
| 기술 성숙도와 실제 시장 채택·생태계 지원 수준 사이에 차이가 있는가 | 연구 성과는 높지만 도입이 적거나, 시장 관심에 비해 검증이 부족한지 |
| 보고된 장점이 특정 환경이나  조건에서만 성립하는가 | 특정 GPU·context length·batch size·bandwidth 등 전제조건에 따른 평가 변동 |

## **5-2. State 설계**

| State Key | 타입 | 생성 / 수정 Agent | 역할 |
| :---: | :---: | :---: | ----- |
| selected\_technologies | dict | Human / Selection | 비교 대상 기술 2개 저장 |

| evidence | list | 각 조사 Agent | 주장별 출처·근거 저장  (Reducer: operator.add) |
| missing\_evidence | list | 근거 검증 Agent | 근거 부족 항목 저장 |
| synthesis | dict | 종합 Agent | 관점별 공통점·충돌점 종합 |
| retry\_count | int | 근거 검증 Agent | 재수집 횟수 — 상한 2 |
| report | str | 보고서 생성 Agent | 최종 보고서 본문 |

### **병렬 실행 대비 설계 원칙**

* 병렬 실행은 키를 분리하여 동시 쓰기 충돌을 원천 차단한다.

* evidence는 네 Agent가 동시에 누적해야 하므로 Reducer를 적용한다.

* retry\_count로 루프 상한을 두어 무한 반복과 토큰 낭비를 방지한다.

## **5-3. Agent 구성 근거**

| 조정 | 내용 | 근거 |
| :---: | ----- | ----- |
| TRL 평가 Agent 분리 | 가이드 기본안에는 TRL 전담 Agent가 없어 별도 신설 | TRL은 4개 평가 관점 중 하나로 독립된 판정 기준(9단계)을 가지며, 다른 관점과 조사 대상(저장소·프레임워크·제품 발표)이 달라 프롬프트를 공유할 수 없음 |
| 근거 검증 / 추가 검색 Agent 신설 | 종합 이후 근거 충분성을 검사하고 부족 시 재수집하는 루프 담당 | 본 과제의 핵심 제약인 중립성·확증편향 방지를 프롬프트 지시가 아닌 그래프 구조로 강제하기 위함. 검증과 재수집을 분리해야 루프 종료 조건을 명확히 제어할 수 있음 |

| Branch (Fan-out) | 기술 조사 결과를 기반으로 TRL·시장성·이해관계자·도메인 평가 Agent를 병렬 실행하며, 관점별 State key를 분리해 충돌을 방지 |
| Branch (Conditional) | 근거 충분? → Yes: 보고서 생성 / No: 추가 검색 후 근거가 부족한 평가 Agent로 분기 |
| Loop | 근거 검증 → 근거 부족 → 추가 검색 → 해당 평가 Agent 재실행 → 해당 State 갱신 → 다시 종합 → 다시 근거 검증 (최대 2회) |
