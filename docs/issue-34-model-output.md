# 이슈 #34 — 실제 평가의 구조화 출력 실패 복구

#35의 자동 Retriever 연결과 논문 기술 조사를 기반으로 합니다.

`ModelOutputError`는 JSON/schema 오류뿐 아니라 생성 잘림, 출처·인용 불일치,
측정값·실험 조건 불일치를 포함합니다. 관점별 실패 건수만으로 프롬프트 오류라고
단정할 수 없으므로, provider는 관점·기술 ID와 검증 실패 이유를 로그에 남깁니다.
Pydantic 오류에는 오류 종류만 포함하고 원문 응답·입력 값은 기록하지 않습니다.

## 변경

- Ollama의 `done_reason=length`를 구분합니다. 전체 응답이 잘리면 최대 3질문씩
  한 번 분할하여 재추출합니다. 분할 호출도 잘리면 즉시 실패하고 반복 분할하지 않습니다.
  15질문의 경우 최초 호출 1회와 분할 호출 최대 5회이며, 각 분할의 JSON/schema 검증은
  기존처럼 최대 2회입니다. 타임아웃·연결 오류는 이 분할 복구 대상으로 삼지 않습니다.
- 요청별 JSON Schema에서 질문 ID 외에 인용·측정값의 출처 ID도 입력 출처로 제한합니다.
  공통 지시에서 현재 요청의 질문 목록을 우선하고 `unknown`은 빈 인용·측정값을 요구합니다.
- 네 관점의 최초 추출과 인용 재추출 모두 원문 문장과 겹치는 300자 이하 구간을 후보로 만들고,
  출처 ID와 해당 출처의 후보 인용을 JSON Schema로 함께 제한합니다. 모델이 의역을
  반복해 전체 평가를 실패시키는 경로를 줄이며, 최종 원문 일치 검사는 유지합니다.
  native schema는 system 메시지에 중복 삽입하지 않아 문맥 낭비를 줄입니다.
- 원문과 맞지 않는 측정값도 해당 질문만 한 번 재추출합니다. 재추출 뒤에도 숫자·조건이
  같은 인용에 없으면 실패합니다. 확인할 수 없는 결과는 모델이 `unknown`으로 반환할 수
  있으며, 이때 관련 인용·측정값을 판정과 근거에 사용하지 않습니다.
- 이미 `unknown`인 답에 남은 측정값은 버립니다. 사용하지 않을 측정값 때문에 다른 정상
  질문까지 폐기하지 않습니다.

워크플로의 선택적 재검색과 최대 2회 제한, 공유 모델 Lock, 기본 offline 실행은 유지합니다.
최종 `ModelOutputError`의 오류 코드와 `retryable=False` 계약도 유지합니다.
내부 추출 복구 호출은 추가 검색 회차가 아니지만 실제 실행 시간은 늘어날 수 있습니다.

## 회귀 검증

`tests/test_model_output_recovery.py`는 실제 Ollama adapter를 통과하는 HTTP fixture로
생성 잘림·분할 복구·지속 실패 상한을 검증합니다. 추가로 출처 ID schema 제한,
안전한 오류 진단, 측정값 부분 재추출, unknown의 미사용 측정값 제거를 검사합니다.
기존 조작된 인용·측정값 거부 및 선택적 retry/E2E 테스트도 함께 실행합니다.

## 실제 실행 확인 범위

#35의 RAG가 연결된 real workflow(timeout=600)에서 두 기술의 논문 조사가 완료됐습니다.
최초 인용에도 원문 후보 제약을 적용한 후, TurboQuant의 네 관점과 ITME의 TRL까지
반환된 5건에서 ModelOutputError가 없었고 TRL 두 기술은 모두 assessed였습니다.
사용자 요청에 따라 이 시점에 PR을 제출합니다. 나머지 평가·검증·최대 2회 재검색까지의
전체 real 실행 완료는 이 결과에 포함하지 않습니다. 전체 흐름·실패·재시도는 오프라인
회귀 테스트로 별도 검증했습니다.
